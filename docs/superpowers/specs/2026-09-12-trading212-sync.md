# Sync da carteira Trading212 (API v0)

Data: 2026-09-12. Substitui o estudo de viabilidade de 2026-06-22
(`2026-06-22-trading212-integracao.md`), cujos detalhes de API eram de
memória — estes foram confirmados nos docs.

## Factos da API (docs.trading212.com/api, lidos 2026-09-12)

- **Base URL:** `https://live.trading212.com/api/v0` · demo:
  `https://demo.trading212.com/api/v0`.
- **Auth:** dois esquemas, ambos aceitos por todas as operações —
  `legacyApiKeyHeader` (`Authorization: <chave>`) e `authWithSecretKey`
  (`Authorization: Basic base64(chave:secret)`). Usamos Basic quando existe
  `TRADING212_API_SECRET`, senão a chave direta.
- **Só contas Invest / Stocks ISA.** CFD e SIPP não têm API.
- **Endpoints usados:**
  - `GET /equity/account/summary` (1 req/5s) →
    `investments.totalCost`, `investments.currentValue`,
    `investments.unrealizedProfitLoss`, `cash.*`, `totalValue`, `currency`.
  - `GET /equity/positions` (1 req/1s) → array sem envelope nem paginação:
    `instrument{ticker,name,isin,currency}`, `quantity`,
    `averagePricePaid`, `currentPrice`,
    `walletImpact{currency,currentValue,totalCost,unrealizedProfitLoss,fxImpact}`.
- **Moedas:** `averagePricePaid`/`currentPrice` vêm na moeda do
  **instrumento**; `walletImpact.*` na moeda da **conta**.
- **Erros:** 401 chave má · 403 scope em falta · **408 "Timed-out" é um
  resultado normal documentado** · 429 com `x-ratelimit-*` (`reset` = epoch
  em segundos). O corpo de erro **não tem schema** — é opaco.
- **CORS:** não documentado. Irrelevante: a auth é um segredo de longa
  duração, logo tem de ficar no servidor de qualquer forma.
- **IP allowlist:** opcional por chave. Tem de ficar em *Unrestricted* — as
  funções Vercel não têm IP de saída fixo fora do Secure Compute.

## Arquitetura

```
T212View / InvestmentsView
   │  t212Status() · t212Sync() · t212CleanupManual(ids)   (src/lib/trading212Api.js)
   ▼
POST /api/t212            ← token Firebase + ALLOWED_EMAILS (+ TRADING212_OWNER_EMAIL)
   │
   ├─ api/_lib/t212Client.js   chave/secret, base URL, retries 429/408, erros nossos
   ├─ api/_lib/t212Map.js      respostas → forma da app (puro)
   └─ api/_lib/t212Sync.js     escreve com a Admin SDK (único caminho de escrita)
                                  │
/api/cron/t212 (2×/dia) ──────────┘  mesma função, sem UI
```

**Porque a escrita é no servidor:** é o único desenho em que a regra de
mapeamento existe uma vez só e serve tanto o botão como o cron. A
alternativa (proxy fino + mapeamento no cliente) obrigava a duplicar o
mapeamento para o cron.

## Dados

- **Leitura diária** em `users/{uid}/t212Log/t212-<YYYY-MM-DD>`:
  `baseCusto` ← `investments.totalCost`, `valorAtual` ←
  `investments.currentValue`, `source:'t212'`. Id determinístico pela data →
  correr a sync N vezes no mesmo dia faz **upsert**, não duplica.
- **Posições** em `users/{uid}/positions/t212-<ticker>`:
  `{ broker:'Trading212', asset, qty, avgPrice, currentPrice, source:'t212',
  ticker, isin, currency }`.
  **Preços derivados de `walletImpact`** (`totalCost/qty`,
  `currentValue/qty`) porque a app calcula valor como `qty × currentPrice`
  (`src/lib/investments.js`) — guardar o preço em USD somaria dólares ao
  património em euros.
- **Meta** no doc raiz: `t212Sync { enabled, lastSyncAt, lastReport }`.
  `enabled` é o que o cron usa para saber quem ligou a sync; `lastReport`
  alimenta o corpo do push das 18:00.

**Espelho, não merge.** A cada sync, as posições `source:'t212'` que já não
existem na carteira são apagadas; as manuais de outras corretoras nunca são
tocadas. Na primeira sync, as manuais cujo `broker` bate
`/t(rading)?\s*212/i` são devolvidas em `report.manualCandidates` e a UI
oferece apagá-las (duplicariam o património). `cleanup_manual` recusa apagar
posições geridas pela sync.

## Conflito com o diff do cliente

O store carrega uma vez (`loadUserData`) e grava por diff de ids
(`computeDiff`) — **não há `onSnapshot`**. Consequências desenhadas:

1. Linhas escritas pelo servidor não estão no `prev` do cliente, logo o
   cliente **nunca as apaga** por engano.
2. Em troca, também não as vê até recarregar → a UI chama `loadUser(uid)`
   depois de cada sync.
3. Ids estáveis (por ticker/data) evitam o cenário de ressurreição: uma
   posição que se mantém conserva o id, em vez de morrer e nascer com outro.

## Segurança

- Chave só em env de servidor (`TRADING212_API_KEY`, opcional
  `TRADING212_API_SECRET`), nunca no cliente, nunca no Firestore.
- Porta do endpoint igual à do `api/saltedge.js`: token Firebase verificado +
  `ALLOWED_EMAILS`. `TRADING212_OWNER_EMAIL` (opcional) restringe a carteira
  a um dos emails da allowlist — sem isso, qualquer email autorizado veria o
  património de quem configurou a chave.
- Cron protegido por `CRON_SECRET` com a **mesma função** do cron dos
  lembretes (importada, não copiada) e 404 em vez de 401.
- Mensagens de erro são nossas; o corpo cru da T212 nunca é reencaminhado.
- Scopes mínimos na chave: `account`, `portfolio` (+ `metadata` se algum dia
  se usar `metadata/instruments`). Nenhum `orders:*`.

## Agenda

`vercel.json`: `/api/cron/t212` às **16:30 UTC** (antes do lembrete das
18:00 de Lisboa, para o push levar o valor do dia) e às **22:10 UTC** (depois
do fecho americano, valor de fecho). Os dois escrevem o mesmo doc do dia — o
segundo sobrepõe-se ao primeiro.

## Configuração

```bash
vercel env add TRADING212_API_KEY production
vercel env add TRADING212_API_KEY preview react
# opcional, se a chave vier com par Key+Secret
vercel env add TRADING212_API_SECRET production
# opcional: live (omissão) ou demo
vercel env add TRADING212_ENV production
# opcional: restringe a carteira a um email da allowlist
vercel env add TRADING212_OWNER_EMAIL production
```

Local: `.env.local` (nunca `vercel env add … development`, que ecoa o valor
em texto limpo no terminal).
